# HyperLogLog++ sketches

The [`hyperloglog` module](../lib/hyperloglog.shenmod) estimates how many distinct keys a stream
contains. It keeps a bounded sketch, ignores repeated keys, and merges sketches by taking the
maximum rank for each register. It is typed Shen over one primitive, `shen-jit.xxh64`, which hashes
with the runtime's copy of XXH64, so it also runs on static builds.

```sh
shen-jit eval -m hyperloglog \
  -e '(let S (hyperloglog.new 14)
         _ (hyperloglog.add-string! S "one")
         _ (hyperloglog.add-string! S "two")
         _ (hyperloglog.add-string! S "one")
      (hyperloglog.estimate S))'
```

This gives an estimate close to 2. To use the module in a program, add `hyperloglog` to its
descriptor's `requires` and use its `hyperloglog` namespace.

## Functions

| Function | Types and behavior |
| --- | --- |
| `(hyperloglog.new P)` | `fixnum --> hyperloglog.t`. Precision `P` from 4 to 18. |
| `(hyperloglog.add-string! S Text)` | Add the bytes of a string, hashed where they are, and return `S`. |
| `(hyperloglog.add! S View)` | Add the bytes of a `buffer.view` and return `S`. |
| `(hyperloglog.add-fixed! S View Width)` | Add each of the consecutive `Width`-byte keys of a view and return `S`. `Width` is a positive `fixnum`, and the view's length must be a multiple of it. |
| `(hyperloglog.hash-bytes View)` | The `word.t` hash of a view's bytes, seed-zero XXH64. |
| `(hyperloglog.add-hash! S H)` | Add a uniformly distributed 64-bit hash of type `word.t`. |
| `(hyperloglog.add-hashes! S Hashes)` | Add all hashes in a `words.t` array. |
| `(hyperloglog.merge! S Other)` | Merge `Other` into `S` and return `S`. Both sketches must have the same precision. |
| `(hyperloglog.estimate S)` | Estimated cardinality as a `float`. |
| `hyperloglog.precision`, `hyperloglog.sparse?`, `hyperloglog.storage-bytes` | Precision, whether the sketch uses sparse storage, and the number of bytes in its storage buffer. |

A sketch is mutable. Use one owner while updating it, or build a sketch in each isolate and merge
their results. A string and a view holding the same bytes are the same key, and
`(hyperloglog.add-hash! S (hyperloglog.hash-bytes View))` adds the same key as `(hyperloglog.add! S View)`.

For packed records, `(hyperloglog.add-fixed! S (buffer.from-string "abcdefghABCDEFGH") 8)`
adds two eight-byte keys. The first key starts at the beginning of the view, so a slice can
start at any byte offset. An empty view adds no keys. The width and the view are checked before
the first key goes in. The keys are hashed eight at a time, which shares the cost of a call to C
among them.

Adding a key allocates nothing unless the sparse table grows or becomes dense: its hash is
written into 8 bytes the sketch keeps, and read from there into a register.

## Storage and estimation

The sparse table starts at 16 bytes. Each occupied cell stores a 25-bit hash prefix and a 6-bit
rank. The table grows at 75% occupancy and becomes dense when the next table would exceed the
dense size, `2^P` bytes, one byte a register. Growing and becoming dense allocate a new buffer.
Runs of cells, as `add-hashes!` and `add-fixed!` make them and a merge reads them, go into the
table by native code, and a merge of dense sketches takes the greater of 16 registers at a time
with vector registers, written with [`native`](guide.md#native-code-by-hand), which the
module loads.

Sparse estimates use linear counting at precision 25. Dense estimates use the precision-specific
linear-counting cutoffs from the HLL++ appendix. Above that range the estimator uses the harmonic
mean, with an empirical bias correction for raw estimates below five times the number of
registers. The expected large-cardinality relative standard error is about `1.04 / sqrt(2^P)`.
At precision 14, the dense buffer is 16 KiB and that error is about 0.81%.

The bias table is generated by a deterministic simulation of the raw estimator and interpolation
between measured points. Its entries are normalized by register count. The generator reproduces
it in the source tree with a C compiler:

```sh
cc -std=c11 -O3 -ffp-contract=off tools/hyperloglog-calibrate.c -lm -o /tmp/hyperloglog-calibrate
/tmp/hyperloglog-calibrate > lib/hyperloglog/bias.shen
```

The design follows the [HyperLogLog++ paper](https://stefanheule.com/papers/edbt13-hyperloglog.pdf)
and its [appendix](https://docs.google.com/document/d/1gyjfMHy43U9OWBXxfaeG-3MjGzejW1dlpyMwEYAAWEI/mobilebasic).

## Verification

`make test-hyperloglog` checks hashes of the vendored XXH64 at 19 lengths, sparse and dense
estimates, merges, and promotion. It compares strings, views, packed batches and prehashed inserts
with one another, byte for byte, across key widths and storage transitions, and checks that
adding keys of each kind to warm sketches adds no collections under allocation stress. Passing
`bench` to the saved test, built from `tests/test-hyperloglog.shenmod`, times each way in over
2,048 keys of 32 bytes, and a merge of dense sketches.
